# go-template

A Go service template: HTTP server, layered handlers, SQLite with typed queries,
and CI wired to the shared reusable workflows.

## Getting started

Create a repository from this template, then claim the name:

```bash
./scripts/init.sh my-service           # or: ./scripts/init.sh my-service some-org
cp my-service.example.yaml my-service.yaml
make run
```

`init.sh` replaces the `REPO_NAME` / `REPO_NAME_UPPER` placeholders, renames
`cmd/REPO_NAME` and the example config, tidies `go.mod`, re-runs `gofmt`, and
deletes itself.

Then check it: `curl localhost:8080/api/livez` and `curl localhost:8080/`.

## Layout

```
cmd/REPO_NAME/         entry point; config struct, defaults and wiring
internal/server/       builds the mux and serves it
internal/api/          JSON API under /api (liveness endpoint included)
internal/web/          HTML pages and embedded static assets
internal/db/           connection + embedded golang-migrate migrations
internal/db/queries/   .sql files sqlc turns into typed Go
internal/db/models/    generated by sqlc — do not edit, and keep it committed
```

`internal/db/models/` is generated but checked in: CI regenerates it and fails
if the result differs, so a stale commit is caught rather than silently used.

## Configuration

Config is layered by [build-with-go/config][bwg]: built-in defaults, then
`REPO_NAME.yaml`, then the environment. The YAML file is gitignored — commit
changes to `REPO_NAME.example.yaml` instead.

Environment variables take the `REPO_NAME_UPPER_` prefix and a double
underscore for nesting:

```bash
REPO_NAME_UPPER_SERVER__PORT=9000 REPO_NAME_UPPER_LOGGER__LEVEL=debug make run
```

[bwg]: https://github.com/pushkar-anand/build-with-go

## Make targets

| Target                       | What it does                                     |
| ---------------------------- | ------------------------------------------------ |
| `make build`                 | Regenerate, then build into `bin/`                |
| `make run`                   | Build and run                                     |
| `make test`                  | `go test -race -count=1 ./...`                    |
| `make cover`                 | Tests with a coverage profile and summary         |
| `make vet` / `make lint`     | `go vet` / `staticcheck`                          |
| `make fmt`                   | `go fmt` + `goimports` (what the CI autoformatter runs) |
| `make gen`                   | Regenerate sqlc models                            |
| `make new_migration name=x`  | Create the next migration pair                    |
| `make tidy` / `make clean`   | Sync `go.mod` / remove build artifacts            |

Tools (`sqlc`, `migrate`, `goimports`, `staticcheck`) come from the `tool`
directive in `go.mod`, so there is nothing to install separately.

Set build tags per invocation with `TAGS`, e.g. `make test TAGS=integration`,
and mirror them in `.github/workflows/ci.yml` via the `build-tags` input.

## Database

SQLite through [mattn/go-sqlite3][m], which is cgo-backed: builds and tests need
`CGO_ENABLED=1`. Swapping engines means changing the driver import in
`internal/db/db.go`, the migrate driver in `internal/db/migrate.go`, and
`engine:` in `sqlc.yaml`.

`db.New` runs every pending migration at startup, so adding a file under
`internal/db/migrations/` is all it takes:

```bash
make new_migration name=add_posts
```

[m]: https://github.com/mattn/go-sqlite3

## CI

Three workflows call the reusable ones in [pushkar-anand/.github][gh]:

- `ci.yml` — verify, tidy check, generate check, build, vet, gofmt, test, and
  staticcheck reported inline on the PR.
- `cover.yml` — coverage, posted as a PR comment and diffed against `main`.
- `autoformat.yml` — runs `make fmt` and commits the result to the PR branch.

[gh]: https://github.com/pushkar-anand/.github
